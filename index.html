Bitmap SDK

On-chain Bitmap and Parcel validation, data, geometry, provenance and indexing.

One JavaScript API for:

  • canonical Bitmap validation
  • Parcel validation and tie-breaks
  • Mondrian geometry
  • parent / child provenance
  • same-sat reinscriptions
  • shared, versioned IndexedDB indexing when the browser storage context allows it
  • live block updates

Bitmap validation


Validate a Bitmap and resolve its canonical inscription.


const bitmap =
  await BitmapSDK.validateBitmap(
    177700
  )

const inscriptionId =
  await BitmapSDK.getBitmapInscriptionId(
    177700
  )

const sat =
  await BitmapSDK.getBitmapSat(
    177700
  )


For application-ready data:


const data =
  await BitmapSDK.getBitmapData(
    177700
  )


The historical <942k OCI is used as an accelerator for older Bitmaps. The SDK verifies canonical claims and can fall back to live block scanning where required.






Parcel validation


Validate one Parcel:


const parcel =
  await BitmapSDK.validateParcel(
    0,
    177700
  )


Get the canonical Parcel inscription:


const id =
  await BitmapSDK.getParcelInscriptionId(
    0,
    177700
  )


Get all canonical Parcels:


const parcels =
  await BitmapSDK.getBitmapParcels(
    177700
  )


Validate a specific inscription as a Parcel:


const result =
  await BitmapSDK.validateParcelInscription(
    'INSCRIPTION_ID'
  )


Do not assume an inscription is a canonical Parcel simply because its body looks like 0.177700.bitmap. The SDK checks the Bitmap relationship, transaction range, direct-parent provenance and canonical tie-break.






Mondrian geometry


Return the deterministic Bitmap Parcel layout.


const mondrian =
  await BitmapSDK.getBitmapMondrian(
    177700,
    {
      includeClaims: true
    }
  )

for (const slot of mondrian.slots) {
  console.log(
    slot.parcelNumber,
    slot.x,
    slot.y,
    slot.size,
    slot.claimed,
    slot.inscriptionId
  )
}


The underlying pattern can also be requested directly:


const pattern =
  await BitmapSDK.getBitmapPattern(
    177700
  )






Children and provenance


Build the parent / child provenance graph of an inscription.


const graph =
  await BitmapSDK.getChildrenTree(
    inscriptionId,
    {
      maxDepth: 3,
      maxNodes: 1000
    }
  )

console.log(graph.nodes)
console.log(graph.edges)


For a complete Bitmap view:


const tree =
  await BitmapSDK.getBitmapTree(
    177700,
    {
      maxDepth: 3,
      maxNodes: 1000,
      includeReinscriptions: 'root'
    }
  )

console.log(tree.bitmap)
console.log(tree.parcels)
console.log(tree.provenance)
console.log(tree.reinscriptions)


The provenance result uses nodes and edges because inscriptions can have multiple parents. Do not assume every inscription relationship is a simple one-parent tree.






Reinscriptions


Get inscriptions that share the same sat.


const chain =
  await BitmapSDK.getReinscriptionChain(
    inscriptionId
  )

if (chain.supported === false) {
  console.log('Sat index unavailable')
}


Parent / child provenance and same-sat reinscriptions are separate relationships.






Shared IndexedDB storage


Bitmap SDK uses one stable IndexedDB database name, bitmap-sdk, as an optional local Bitmap data layer. This is useful for more than simple caching: compatible apps running in the same browser origin and storage context can reuse data that another Bitmap SDK app has already validated.



Why this is useful


    

  • Less repeated network work. A Bitmap, Parcel set, Mondrian layout or provenance tree that has already been validated can be reused instead of being rebuilt from recursive endpoints every time.
    • 

  • A common local Bitmap index. Different inscriptions using Bitmap SDK can converge on the same browser-side data model instead of each app inventing its own incompatible cache.
    • 

  • Faster second and later apps. As the local index fills, compatible SDK apps can start with more data already available.
    • 

  • Validation rules are versioned. Stored records carry bitmap-sdk-v1.0.1. Bitmap SDK refuses old validation-derived records after the protocol/storage rules change, preventing stale results from silently becoming authoritative.
    • 

  • Live updates can be shared. The SDK uses the same storage namespace and a same-origin BroadcastChannel when available, so open SDK apps can react to locally discovered updates.
    • 




Shared does not mean global.
IndexedDB is scoped by the browser's origin/storage partition. Two compatible inscriptions can reuse the same bitmap-sdk database only when the browser gives them the same storage context. A different Ord host, browser profile, private session, or isolated/sandboxed context will have a different database or no persistent storage at all.



Ord iframe caveat.
Ord commonly renders inscription previews inside sandboxed iframes. A sandboxed preview may receive an opaque/isolated origin, in which case IndexedDB sharing can be unavailable. Bitmap SDK detects unavailable storage and continues from memory plus recursive Bitcoin/Ord data. Storage is an accelerator, never the source of truth.



Storage identity


BitmapSDK.STORAGE_DB_NAME
// "bitmap-sdk"

BitmapSDK.STORAGE_DB_VERSION
// 2

BitmapSDK.STORAGE_PROTOCOL_VERSION
// "bitmap-sdk-v1.0.1"



Use it


await BitmapSDK.storage.ready()

const status =
  await BitmapSDK.storage.getStatus()

console.log(status)

// Read already stored canonical data.
const bitmap =
  await BitmapSDK.storage.getBitmap(177700)

const parcels =
  await BitmapSDK.storage.getBitmapParcels(177700)

// Listen for same-context SDK storage updates.
const unsubscribe =
  BitmapSDK.storage.subscribe(event => {
    console.log(event)
  })

// Later:
unsubscribe()



Recommended standard: Bitmap apps should use the SDK storage layer instead of creating a separate Bitmap database unless they genuinely need application-specific data. App-specific UI state can live elsewhere; canonical Bitmap/Parcel validation data should remain in the SDK's shared schema.

Block watcher


Watch sequential Bitcoin blocks for new canonical Bitmap and Parcel updates. The default watcher is deliberately fast: it does not deep-fetch every encoded/delegated inscription in a block. Set resolveEncodedParcelCandidates:true only when exhaustive discovery is worth the extra network cost.


const watcher =
  BitmapSDK.watchBlocks(
    event => {
      console.log(event.newBitmaps)
      console.log(event.newParcels)
    },
    {
      pollIntervalMs: 30000,
      scanCurrent: true,
      persist: true,
      resumeFromStorage: true,

      // Fast/default watcher mode. Encoded/delegated
      // candidates are deferred rather than deep-fetched.
      resolveEncodedParcelCandidates: false
    }
  )

await watcher.ready

// Later:
watcher.stop()
